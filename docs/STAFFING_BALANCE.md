# 助手編制與玩法驗證

## 採用設定

助手不含候選人。採用 **2 → 3 → 4**，素人與政二代開局 2 位，現任開局 3 位。招募占用一個主要行程，下一回合到職，沿用按剩餘天數預付薪資。所有助手共用研究、直播、募款攤與隨行工作的人力池。

這個選擇主要是減少過早全面完成研究，讓每多一人都值得分配。現任由 4 人減至 3 人是恢復招募選擇的節奏調整，不能據此宣稱勝率平衡已達標。

## 隔離人數變化的對照

引擎與策略凍結在 `a3c32325891f7e37fc2417167e020421284049ea`。每種編制使用相同種子 1–100、三種身分、無黨籍與國民黨、五種行為規則，共 9,000 局。只替換助手階梯與一致的上限檢查，開局保留原 2 / 2 / 4；現任開局 3 人另做 500 局測試。這些資料隔離人數效果，並非同時包含新小隊、新曝光遞減等機制的整合成績。

五種規則：前兩回合盡量招募、之後主角募款與助手研究；相同行為但不招募；招募後準備議題、上電視；不招募的電視對照；原先讀人群的適應策略。研究優先補未知，再深入研究，募款攤保留一人；資源路線第 7 回合參加政見會、最後兩回合跑市場。

## 重現

先從上述 commit 匯出 `dist/day-engine.js` 與 `tests/strategy-balance.cjs` 成兩個暫存檔，再執行：

```sh
node scripts/staffing-comparison.cjs --engine /tmp/staffing-baseline-engine.cjs --harness /tmp/staffing-baseline-policy.cjs --seeds 100 --output /tmp/staffing-paired.json
node scripts/staffing-comparison.cjs --engine /tmp/staffing-baseline-engine.cjs --harness /tmp/staffing-baseline-policy.cjs --seeds 100 --parties independent --identities incumbent --ladders 234 --incumbent-start 3 --output /tmp/staffing-incumbent-three.json
```

腳本以輸入原始碼的 SHA-256 記錄版本，可用 `--detail yes` 保存逐局資料。「全題完成回合」只計達成的局，必須與達成比例一起閱讀。平均票數、勝率是腳本表現，不是人類試玩的可玩性證明。比較腳本也保存招募與公開行程次數；上述政二代募款研究路線的三種編制都使用兩回合招募，只剩三回合公開行程，新增助手不會創造額外主行程。

## 整合玩法驗證

完整平衡門檻沿用 `REQUIREMENTS.md` R15，沒有降低。策略檢查納入地方小隊、接續直播與招滿人研究募款打法；所有作答只讀畫面提供的方向／臉與改口標籤，不讀個別選民或預估票數。也修正舊策略在電視／政見會安排助手研究（實際介面沒有這個操作）的不一致；新舊策略分數不能全歸因於遊戲數值。

### 驗證版本與方法

整合數值的引擎 SHA-256 為 `df21bce5834dbfaa6987832c599c8232f5344318e408d7755c916d5ba7bf257b`，策略 SHA-256 為 `5ef3f8c3815ad4675afdf7779c145715be6eaa9cb4363d2d62769f75303d89b1`。每個身分以 10001–10030 搜尋固定路線，再用 1–150 評估；三個身分分開執行，最後交給同一份原始門檻判定。固定路線的完整行程、地點、研究、經費、合作與回答規則都保存，不能只用顯示名稱還原。

本輪也修正了小隊的預設政見與撤回後的替補邏輯。前一份完整執行的 hash `4fd3422722900b24030fe88c674f66bb3b671053a64ec02bf4bdc2e255b503d9` 只作歷史對照；即使數值常數相同，預設政見不同仍會影響票數，沒有把那份結果當作最終版本。

### 可重現性與限制

本機原始資料位於忽略版控的 `scratch/staffing-comparison-2026-10-23/`：`paired-100.json`、`incumbent-three-100.json`、`final-{newcomer,heir,incumbent}.json`、`final-balance-150.json`、`final-adaptive-grades-150.json`、`final-tv-comparison.json`、`r4-*.json` 與 `followup-*.json`。上述摘要保留於本文件；完整門檻仍可用 `npm run test:balance` 從目前程式重新搜尋與評估。

適應腳本只使用當下可見資訊，但並不是完美玩家：作答採用目前畫面符號，出發前估值仍主要用方向，沒有把所有本人研究強弱、敘事情境與長期取捨都最佳化。不同策略名稱也不自動算不同玩法；門檻以實際行程比例的距離判定。平衡失敗是需要保留的證據，不能靠降低門檻或為了通過持續新增有利測試路線消除。
